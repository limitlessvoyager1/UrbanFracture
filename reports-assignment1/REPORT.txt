A1-01 — ACTIONABILITY PROJECTION DISAGREES WITH OFFENSIVE ELIGIBILITY
Status: confirmed diagnostic inconsistency; gameplay bypass NOT reproduced.
Root cause: continuity296.resolve lists stun/shock/down/recovering/standingLock/wakeInv/guardBreak but omits reassessUntil274 (and native cooldown). Its unqualified actionable field becomes true while combat274 still rejects offensive starts.
Affected: all8families under heavy tests and6under light/medium in this matrix; both heroes. No level-specific scope established.
Sources: dist/continuity296.js resolve; dist/combat274.js defer; diagnostic consumers must be inventoried before implementation.
Reproduce: run audit tool; inspect audit.json projection. Example Marcus heavy at t0.5166667: stun/down/recovery0, state idle/actionabletrue, enforced deadline0.5666667; both direct start and enemyAct still reject offense.40cases recorded.
Proposed correction: define explicitly separate locomotion/presentation freedom and offensive eligibility in read-only diagnostics, deriving reassessment remaining from actual actor deadline/time and retaining native cooldown semantics. Audit consumers before deciding whether to rename/add fields. Keep physical start guards and visual state unchanged.
Regression risks: treating utility/guard/locomotion as prohibited offense; misrepresenting paired or specialized AI states; accidentally using diagnostic state to drive mechanics.
Tests: record projection versus both entry paths before/during/after deadline, actual stun/recovery/cooldown boundaries, paired exceptions; run14suites and byte/trajectory parity. Current tool records mismatch rather than claiming desired projection contract passes.
Priority: first scoped repair proposal. Acceptance: diagnostics accurately distinguish offensive lock from locomotion freedom; HP/frame data and existing admission trajectory identical.
